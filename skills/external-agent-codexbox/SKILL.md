# External Agent Codexbox

## 1. 定位与职责

`cxbox` 是运行在独立 Ubuntu 环境中的 Codex Agent，通过 SSH 接入 ChatGPT App，以远程项目中的独立聊天承接任务。它是具备自主调查、推理、实施和验证能力的 External Agent，不属于内置 subagent。

- **Main Agent**：用户的默认交互入口，负责需求理解、全局协调、关键决策、结果验收和最终交付。
- **cxbox**：在明确的任务与授权边界内自主规划、调查、实施和验证，可独立承担复杂、多步骤任务。
- **协作目标**：充分利用 cxbox 的独立执行能力，在保证正确性和交付质量的前提下，减少 Main 的 Token 与上下文消耗，避免在主对话中充斥大量嘈杂的中间输出内容。

## 2. 动态任务委派

### 默认策略

Main 直接处理轻量任务和关键决策；对于目标独立、结果可验证且委派收益明显的工作，优先使用 cxbox：

- 批量搜索、代码阅读、日志分析、问题调查和信息提取。
- 功能实现、故障修复、配置调整、测试与验证。
- 需要大量工具操作或产生较多中间上下文的任务。
- 可以明确划分执行范围、独立交付并验收的工作。

综合任务独立性、工作量、模型能力、Token 消耗、交接成本和预期收益决定分工。任务复杂不代表必须由 Main 执行；步骤简单也不代表不值得委派。

### Main 直接处理

- 简单问答、轻量操作以及委派成本高于直接处理成本的任务。
- 需求澄清、架构取舍、关键技术决策和跨任务协调。
- 委派结果验收、结论冲突处理和最终交付。

复杂任务可以由 Main 决策、cxbox 执行，不必由 Main 完成全部工作。

### 按需介入与返回

cxbox 默认在任务边界内自主完成工作，出现以下情况时由 Main 介入：

- 多次基于有效证据的尝试仍无法通过验证，且已排除外部阻塞。
- 关键证据相互矛盾，现有调查无法可靠确定根因。
- 出现影响整体方案的重大取舍、范围变化或不可接受的风险。
- 需要超出当前任务边界的关键决策或额外授权。

Main 优先解决具体难点，而非接管完整执行任务。难点解决后，优先让 cxbox 在原会话继续实施和验证。

缺少权限、凭据、文件、网络或工具能力属于外部阻塞，不直接视为模型能力不足。交接成本高于剩余工作量时，由当前执行者完成。

不为普通任务向用户输出路由分析，也不反复征求委派意见。用户明确指定执行者时优先遵从，实际操作仍须满足适用授权和工具限制。

## 3. 派发与任务契约

### 确认执行入口

- **目标识别**：调用 `list_projects`，结合 host、project 和工作目录确认 cxbox，不能只凭项目名称匹配。
- **工具检查**：根据当前工具 schema 确认远程聊天的创建、通信和等待能力，不猜测参数或将工具缺失直接视为 cxbox 不可用。
- **Agent 设置**：默认沿用 cxbox 的模型、推理强度和工具设置，按需调整，不由 Main 强制指定模型。
- **共享文件**：cxbox 通过 `/mnt/mac` 访问 Mac 文件，Mac 通过 `~/OrbStack` 访问 cxbox 文件。使用前确认实际路径和权限，避免重复复制、并发修改或越权访问。

Main 可以根据任务需要自主决定是否委派，但创建聊天、发送消息及实际执行仍须满足当前 App 工具、用户和项目的授权要求。一般性的委派偏好不替代工具要求的明确授权。

### 任务契约

按 `agent-task-prompting` skill 构造任务契约，不假定 cxbox 已掌握 Main 的聊天上下文：

- **目标与验收**：明确任务目标、预期交付物和验收标准。
- **上下文与范围**：提供必要背景、文件路径、已有决策、执行范围和适用授权。
- **执行自主性**：允许 cxbox 在边界内自行调查、修改、调整方案和验证，不把具体命令或步骤限制为固定白名单。
- **阻塞边界**：必要输入缺失时先自主排查；仍无法解决或需要额外授权时，报告证据、原因及恢复条件。
- **结果交付**：简洁返回结论、关键证据、验证结果和遗留问题；修改任务列出变更路径及验证结果。

保留必要的原始证据，不传递无关历史或不必要的敏感信息。大量探索、日志和测试过程留在 cxbox 上下文中，Main 只保留关键发现和决策信息。

## 4. 会话与并发管理

### 会话生命周期

- **创建**：满足工具授权要求后，通过 `create_thread` 在已确认的远程 `projectId` 创建独立聊天，保存 `threadId` 和 `hostId`。
- **标识校验**：`clientThreadId` 不等于 `threadId`；仅获得前者时，先通过可用状态入口确认实际 Thread，不重复创建状态未明的任务。
- **等待**：优先使用 `wait_threads`，续等时将返回的 cursor 作为 `afterCursor`，避免频繁轮询和重复读取。
- **续传**：确认已保存的 `threadId` 和 `hostId` 属于当前任务，且发送已获授权后，用 `send_message_to_thread` 发送增量补充、纠偏或后续验证。标识缺失时，只读取该任务的候选会话核对，不扫描其他会话。
- **详细检查**：仅在验收、排障或需要关键证据时使用 `read_thread`，限定读取范围和输出量。

工具接受创建或发送请求，不代表远端任务已执行或完成。状态不明时先确认，不重复派发可能冲突的操作。

不同任务默认使用独立聊天。归属只认创建时保存的 `threadId` 与 `hostId`，或用户明确给出的会话标识；指定 cxbox 或项目不算指定会话。

- 同项目、同主机、会话空闲或模型可用，不能作为归属依据。不为复用环境或绕过故障，把任务改发到其他会话。
- 原会话仍可通信时继续使用。原会话失效或偏离目标时，在创建已获授权且工具允许的前提下，新建聊天并传入必要上下文。
- 无法新建，且没有本次任务会话或用户指定会话时，报告限制。Main 只承接授权范围内少量可独立完成的剩余工作；大块未完成的委派任务保持阻塞报告。

### 任务拆分与并发

Main 可以将相互独立、可分别验收的工作拆分为多个 cxbox 任务并发执行：

- 仅并发执行输入已齐备、无需等待彼此结果的任务；有依赖关系时分阶段推进。
- 只读调查通常可以并发；修改任务必须明确资源范围，避免互相覆盖。
- 独立聊天不代表环境隔离。共享文件、Git 分支、索引及运行环境的冲突操作应串行执行，或使用经确认的隔离环境。
- 默认最多同时执行 **3 个 cxbox 任务**，根据实际资源负载、任务独立性及工具限制调整并发数量。
- 维护任务与 `threadId`、`hostId`、cursor 的对应关系；状态不明的任务仍占用并发名额。

Main 及时派发当前可独立执行的任务，无需逐个等待。任务完成后统一核验结果、解决结论冲突并确认整体目标。

## 5. 验收与异常恢复

### 结果验收

Main 根据任务风险和证据充分性完成必要验收，不常规重复 cxbox 已完成的调查或执行。

- 核对交付物、关键证据、验证结果及未完成事项。
- 修改任务检查共享工作区中的实际变更及验证记录。
- 高风险操作加强独立验证，不仅依赖 cxbox 的总结。
- 验收不通过时，优先在原 Thread 提供具体反馈，让 cxbox 继续修复。

### 异常与恢复

- **工具或授权限制**：区分项目发现、聊天创建、消息发送和实际执行状态；准确识别受限环节，未派发时不声称任务已执行。
- **执行阻塞**：先确认事实并补充必要输入，优先让 cxbox 在原会话恢复。
- **模型或会话故障**：先确认请求是否已执行，以及工具实际支持的模型。结果未确认的修改不重试。只在当前任务会话内重试，或按授权新建替代会话；沿用现有模型与推理设置，不猜测未列出的参数，也不改发到其他会话。
- **任务纠偏**：发生实际越界、违反适用约束、不可接受的风险或用户改变方向时，及时要求调整或暂停。
- **状态不明**：先确认现有执行结果，不盲目重试、重复创建聊天或启动冲突操作。
- **无法恢复**：报告阻塞、已完成内容及剩余工作，不静默由 Main 接管大量已委派工作。

### 用户交互与交付

Main 是统一的用户沟通与交付入口：

- 常规内部委派无需向用户解释执行者选择、Thread 标识或工具调用细节。
- 长时间运行的任务适当汇报进度；出现重大风险、权限阻塞或执行失败时，及时说明实际状态。
- 不将工具请求成功表述为任务完成，不声称尚未执行或验证的工作已经完成。
- 最终交付以任务结果、关键证据、验证情况和遗留问题为主，不输出无关的内部协作过程。

Main 始终承担最终交付责任，cxbox 保持任务范围内的执行自主性；所有实际操作均受当前用户授权、项目约束和工具权限限制。
